# rgy — parity

Two questions, one document: what each operating system gets, and what
Listary does that rgy does not.

**This file is written by hand.** It is the source of truth, and
[`scripts/parity.py`](../scripts/parity.py) is the gate that reads it: a
`G` cell is a gap — work required — and it fails CI until it is ported or
documented as degraded; a Listary gap with no work attached to it is a gap
nobody has scheduled.

**The two tables use the same letters, and `P` means different things in**
**each.** In the matrix, `P` is *ported* (shared code, a platform hook); in
the capabilities, `P` is *parity* (rgy already matches Listary). `D` is
*degraded* in both, and `G` is a *gap* in both.

## The legend

In the matrix: **N** native &middot; **P** ported (shared code, platform hook) &middot;
**D** degraded (documented limit) &middot; **G** gap (work required) &middot; **-** N/A

In the capabilities: **P** parity &middot; **D** degraded &middot; **G** gap

## The Listary capabilities

This is the implementation plan. Every capability Listary has, as recovered
by reverse engineering, and where rgy stands against it. A `G` row is a gap:
the `work` column says what closing it means in rgy's terms, and the phase
says when. A `D` row is where rgy has a weaker version, and the `work`
column says the difference. A `P` row is where rgy already matches, and the
`rgy` column names the code that does it — so the plan does not redo work
that is already done.

| S.10 | Incremental re-ranking on query edit | D | When the query is edited, the executor reuses the previous result set and the previous state instead of re-scanning the index -- a keystroke-latency optimisation, keyed by an incremental-search session id. | Degraded, and the reason is measured.
